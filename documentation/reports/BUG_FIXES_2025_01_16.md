## Bug #1: Backend-Aware Strategy Selection NOT Implemented

### Severity: CRITICAL

**Root Cause:**

The benchmark configuration system hardcoded `"two_opt_simple"` (CPU implementation) for ALL backends, including `"cupy"`. This meant GPU 2-opt strategy was NEVER used despite being correctly implemented.

**Affected Files:**

- `code/examples/benchmark_comprehensive.py` (lines 207-264)

**Evidence:**

```python
# BEFORE (WRONG):
elif algorithm == "ga_2opt":
    algo_config = {
        "backend": backend,  # ← Backend set correctly
        "strategies": {
            "improvement": {
                "name": "two_opt_simple",  # ← HARDCODED CPU!
                "params": {"max_iterations": 10},
            },
        },
    }
```

**Impact:**

- ALL "cupy" backend runs actually used CPU 2-opt
- No GPU kernel execution occurred
- Benchmark results showed NO GPU benefit (because GPU wasn't being used!)
- User confusion about GPU performance

**Fix Implementation:**

```python
# AFTER (CORRECT):
# Lines 207-208 in benchmark_comprehensive.py
improvement_strategy = "two_opt_gpu" if backend == "cupy" else "two_opt_simple"

elif algorithm == "ga_2opt":
    algo_config = {
        "backend": backend,
        "strategies": {
            "improvement": {
                "name": improvement_strategy,  # ← Dynamic selection
                "params": {"max_iterations": 200},  # ← Also fixed Bug #2
            },
        },
    }
```

**Validation:**

```bash
# Test command
uv run python code/examples/benchmark_comprehensive.py \
    --tiers tiny \
    --algorithms ga_2opt \
    --backends numpy cupy

# Output verification:
# NumPy row: "imp=two_opt_simple(max_iterations=200)"
# CuPy row:  "imp=two_opt_gpu(max_iterations=200)"  ← CONFIRMED!
```

## Bug #2: Insufficient 2-opt Iterations in GA

### Severity: HIGH

**Root Cause:**

GA 2-opt improvement was configured with `max_iterations=10`, but problems with n>1000 require 200-500 iterations for convergence. This provided only 2-5% of needed improvement work.

**Affected Files:**

- `code/examples/benchmark_comprehensive.py` (lines 216, 264)

**Evidence:**

From `PHASE_6_COMPLETE_AND_PHASE_7_PLAN.md`:

```python
# Literature (Hoos & Stützle 2005):
# 2-opt iterations needed ≈ 0.2 * n to 0.5 * n
# For pr1002 (n=1002): 200-500 iterations needed
# Current setting: 10 iterations → Only 2-5% of work!
```

**Impact on Quality:**

```
pr1002 WITHOUT sufficient 2-opt: gap = +1361% (catastrophic)
pr1002 WITH 200 iterations 2-opt: gap ≈ +54% (estimated, still needs validation)
```

**Fix Implementation:**

```python
# Line 216 and 264 in benchmark_comprehensive.py
"params": {"max_iterations": 200},  # ← Changed from 10
```

**Rationale:**

- 200 iterations provides 20-100% of needed work for problems n=100-1000
- Balances quality vs runtime (each iteration is O(n²))
- Matches literature recommendations (Voudouris 1999 GLS)

## Bug #3: context.rng NameError in GA Initialization

### Severity: MEDIUM

**Root Cause:**

Genetic Algorithm initialization attempted to use `context.rng.permutation()` but `context` object doesn't have a `rng` attribute. Should use backend's random number generator (`xp.random`).

**Affected Files:**

- `code/src/algorithms/metaheuristics/genetic_algorithm.py` (line 541)

**Error Message:**

```python
NameError: name 'context' is not defined
# OR
AttributeError: 'ProblemContext' object has no attribute 'rng'
```

**Discovery:**

Found during first validation run with NumPy backend on burma14. Crash occurred during population initialization.

**Fix Implementation:**

```python
# Line 541 in genetic_algorithm.py

# BEFORE (WRONG):
initial_tour = context.rng.permutation(customers_array)

# AFTER (CORRECT):
initial_tour = xp.random.permutation(customers_array)
```

**Validation:**

```bash
# NumPy backend now works:
burma14: cost=3323 (OPTIMAL!)
eil51:   cost=573  (+34.51% gap)
```

## Bug #4: CuPy RandomState .random() Incompatibility

### Severity: HIGH

**Root Cause:**

Code used `context.rng.random()` method which exists in NumPy RandomState but NOT in CuPy RandomState. CuPy only provides `.rand()` and `.random_sample()`.

**Affected Files:**

- `code/src/algorithms/metaheuristics/genetic_algorithm.py` (lines 378, 387)

**Error Message:**

```python
AttributeError: 'RandomState' object has no attribute 'random'
```

**API Compatibility Analysis:**

| Method | NumPy RandomState | CuPy RandomState | Universal? |
|--------|-------------------|------------------|------------|
| `.random()` | ✅ Exists | ❌ Missing | ❌ NO |
| `.rand()` | ✅ Exists | ✅ Exists | ✅ YES |
| `.random_sample()` | ✅ Exists | ✅ Exists | ✅ YES |

**Discovery:**

Found during CuPy backend validation. Benchmark crashed on burma14 with AttributeError during crossover/mutation probability checks.

**Fix Implementation:**

```python
# Lines 378 and 387 in genetic_algorithm.py

# BEFORE (WRONG - NumPy only):
if float(context.rng.random()) < crossover_rate:
    # crossover
if float(context.rng.random()) < mutation_rate:
    # mutation

# AFTER (CORRECT - Universal):
if float(context.rng.rand()) < crossover_rate:
    # crossover
if float(context.rng.rand()) < mutation_rate:
    # mutation
```

**Validation:**

```bash
# API test:
>>> import cupy as cp
>>> rng = cp.random.RandomState(42)
>>> hasattr(rng, 'random')
False
>>> hasattr(rng, 'rand')
True
```

## Bug #5: Division by Zero in Speedup Calculation

### Severity: LOW

**Root Cause:**

Speedup calculation performed division without checking if denominator (time_seconds) was greater than zero. When CuPy runs failed (time_seconds=0), this caused ZeroDivisionError.

**Affected Files:**

- `code/examples/benchmark_comprehensive.py` (lines 497-498)

**Error Message:**

```python
ZeroDivisionError: float division by zero
```

**Discovery:**

Occurred when CuPy backend failed (Bug #4), setting time_seconds=0. Speedup calculation then crashed before error could be reported.

**Fix Implementation:**

```python
# Lines 497-498 in benchmark_comprehensive.py

# BEFORE (WRONG):
result.speedup = numpy_result.time_seconds / result.time_seconds

# AFTER (CORRECT):
if result.time_seconds > 0 and numpy_result.time_seconds > 0:
    result.speedup = numpy_result.time_seconds / result.time_seconds
else:
    result.speedup = 0.0  # Failed run, no speedup
```

**Notes:**

- This bug was masked by Bug #4 (only triggered when runs fail)
- Low severity but critical for error reporting
- Allows benchmark to complete even when some configurations fail

## Lessons Learned

### 1. Leaky Abstractions

**Problem:** "Lego bricks" architecture allows invalid compositions.

The backend abstraction permits connecting CPU-only strategies with GPU backends, resulting in silent performance bugs (or catastrophic slowdowns like the 28× SA Random2Opt case).

**Mitigation:** Need validation guards or two-backend system (computation + kernel)

### 2. API Compatibility is NOT Guaranteed

Even "compatible" libraries (NumPy/CuPy) have subtle differences:

- RandomState methods differ
- Must test BOTH backends, not assume compatibility

**Best Practice:** Use only methods guaranteed in both (`.rand()`, not `.random()`)

### 3. Benchmark Configuration Must Be Backend-Aware

Hardcoding strategy names breaks the abstraction. Factory should select strategies dynamically based on backend.

**Pattern:**

```python
# CORRECT:
strategy = "gpu_impl" if backend == "cupy" else "cpu_impl"
```

### 4. Default Parameters Matter

max_iterations=10 seems reasonable for n=50 but fails catastrophically for n=1000. Literature-based defaults critical for quality.

### 5. Error Handling in Benchmarks

Division-by-zero in speedup calculation masked the real error (CuPy crash). Always guard math operations in reporting code.

## Performance Characteristics

### GPU Overhead Analysis

**Tiny Problems (n<100): GPU SLOWER**

| n | NumPy Time | CuPy Time | Speedup | Overhead Ratio |
|---|------------|-----------|---------|----------------|
| 14 | 0.864s | 14.697s | 0.06× | 17× slower |
| 51 | 1.212s | 15.833s | 0.08× | 13× slower |
| 76 | 1.300s | 20.672s | 0.06× | 16× slower |
| 100 | 1.963s | 19.026s | 0.10× | 10× slower |

**Analysis:**

Kernel launch overhead (~500μs) dominates computation time for tiny problems. The 2-opt kernel evaluation is extremely fast (O(n²) but n is small), so fixed overhead is the bottleneck.

**Theoretical Crossover Point:**

From `2opt_parallelization_strategies_comparison.md`:

$$T_{GPU} = T_{launch} + \frac{T_{compute}}{Speedup_{kernel}}$$

$$T_{CPU} = T_{compute}$$

**Break-even when:**

$$T_{launch} + \frac{T_{compute}}{S} = T_{compute}$$

$$T_{launch} = T_{compute} \cdot (1 - \frac{1}{S})$$

For GTX 1050 with $S \approx 10$:

$$T_{compute} = \frac{T_{launch}}{0.9} \approx \frac{500\mu s}{0.9} \approx 556\mu s$$

**Expected crossover: n ≈ 500-1000 cities**

**Hypotheses:**

1. **Insufficient iterations:** Literature suggests pop=500-1000, gen=200-500 for n>100

**Investigation Plan:**

### 3. Implement Two-Backend Architecture (PRIORITY 3)

**Problem:** Current single backend forces invalid compositions (NN + cupy = overhead).

**Solution:** Split into `computation_backend` + `kernel_backend`.

**Design:**

```python
def algorithm(
    context: ProblemContext,
    customers: List[int],
    computation_backend: BackendModule,  # For arrays (numpy/cupy)
    kernel_backend: Optional[BackendModule] = None,  # For CUDA kernels
) -> Tour:
    ...
```

**Semantics:**

- `computation_backend`: Vectorized array ops (distance matrices, array slicing)
- `kernel_backend`: Custom CUDA kernels (2-opt GPU, parallel reductions)

**Benefits:**

- Nearest Neighbor: `computation_backend=cupy`, `kernel_backend=None` (no overhead)
- GA with 2-opt GPU: `computation_backend=cupy`, `kernel_backend=cupy` (full GPU)
- Explicit control, clear semantics

**Estimated Effort:** 2.5 hours (30 files to update)

### 4. Add Safety Rails (PRIORITY 4)

- **VRAM Calculation:** Predict memory before launch, prevent OOM
- **Buffer Reuse:** Allocate O(n²) buffers once in `__init__`, not per iteration
- **S-Task Validation:** Prevent Random2Opt + cupy compositions

### 5. Quick Wins (ANYTIME)

- Add optimal costs from database (enable gap% calculation)
- Fix speedup reporting (show "17× slower" instead of "0.06×")
- Add GPU threshold warning (n<500)
